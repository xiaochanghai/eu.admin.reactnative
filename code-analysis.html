代码概览

技术栈

Expo 57、React Native 0.86、React 19、TypeScript、NativeWind、 Zustand、MMKV、Axios、React Query、JPush。

根入口位于 src/app/_layout.tsx，路由入口为 expo-router/entry。

路由组织

使用 src/app 文件路由。普通用户进入 /(app)，维修用户进入 /(repair)。

通用 Tab

Tab 逻辑封装在 src/components/tabs/tab-layout.tsx， 自定义 TabBar 在 custom-tab-bar.tsx。

核心链路

  1. 启动阶段执行 hydrateAuth()、主题加载、Splash 控制、 隐私协议弹窗、版本检查、JPush 初始化和设备登记。
  2. 登录页位于 src/app/login.tsx，调用 /api/Authorize/Login，成功后保存 token 和 userInfo。

主要问题

高 类型检查当前不可用

运行 pnpm.cmd run type-check 后失败在 tsconfig.json：TypeScript 6 已废弃 baseUrl， 当前配置会让本地和 CI 的类型检查直接中断。

建议先加 "ignoreDeprecations": "6.0" 解除阻塞，随后再规划 TypeScript 7 前的配置迁移。

高 明文记住密码

src/components/login-form.tsx 会把账号和密码写入 MMKV 的 login/credentials。生产环境不建议保存明文密码。

建议改为只记账号，或使用系统 Keychain/Keystore 与生物识别方案。

中 Axios 错误响应没有真正 reject

src/api/common/http.tsx 中业务失败分支调用了 Promise.reject(data)，但没有 return。调用方可能把失败响应当成 成功结果处理。

建议改为 return Promise.reject(data)。

中 登录过期判断可能不一致

响应体业务码使用 data.Status，但异常分支用 response.status === ResultEnum.OVERDUE 判断登出。如果 OVERDUE 是业务码而不是 HTTP 状态码，这里不会生效。

中 中文文本和编码需要专项核查

多个 TSX 文件在控制台读取时出现中文乱码，env.js 通过 rg 显示正常。建议用编辑器确认源文件实际编码，重点检查 src/app/_layout.tsx、src/app/login.tsx、 src/components/login-form.tsx。

低 根布局副作用偏重

根布局同时承担更新检查、推送、设备登记、隐私协议、Provider 和全局弹窗。功能集中但维护成本偏高。

建议逐步拆分为 useAppUpdate、useDeviceRegistration、 usePrivacyGate 等 hook。

具体实现分析

1. 启动与全局 Provider

src/app/_layout.tsx 是应用最核心的启动文件。模块加载阶段直接调用 hydrateAuth() 和 loadSelectedTheme()，因此鉴权与主题会在根组件渲染前先从 MMKV 恢复。随后通过 SplashScreen.preventAutoHideAsync() 接管启动屏隐藏时机。

RootLayout 内部负责注册 JPush、检查 OTA 更新、记录设备信息。Providers 内部再包裹 GestureHandlerRootView、KeyboardProvider、 ThemeProvider、APIProvider 和 BottomSheetModalProvider。 这套组合能保证手势、键盘、主题、React Query 和底部弹窗都在全局可用。

这里的问题是职责过多：根布局既做基础 Provider，又做业务更新检查、隐私协议、推送和设备上报。 这会让启动问题难定位，也让测试变困难。更好的结构是把这些副作用拆成独立 hook。

2. 鉴权状态与持久化

鉴权 store 在 src/lib/auth/index.tsx，使用 Zustand 保存 token 和 status。状态只有三种：idle、 signOut、signIn。hydrate() 从 getToken() 读取本地 token，有 token 就调用 signIn，否则调用 signOut。

token 实际读写在 src/lib/auth/utils.tsx，底层使用 src/lib/storage.tsx 的 MMKV 封装。用户信息也写在 MMKV 的 userInfo key 下。

当前实现简单有效，但 token 没有 refresh 流程，登录时写入的 refresh: 'refresh-token' 是占位值。后端 token 过期后只能走登出或接口失败， 还没有无感刷新能力。

3. 路由守卫与 Tab 布局

TabLayout 位于 src/components/tabs/tab-layout.tsx，它接收 tabConfig，再生成多个 Tabs.Screen。普通模块和维修模块只需要声明 tab 名称、标题和图标，就能复用同一套路由守卫和 Tab 渲染。

守卫逻辑在 Tab 层执行：如果 isFirstTime 为 true，跳转到 /onboarding；如果 status === 'signOut'，跳转到 /login。这意味着进入 /(app) 或 /(repair) 后才会判断登录状态。

自定义 TabBar 在 custom-tab-bar.tsx，通过 navigation.emit({ type: 'tabPress' }) 保留 React Navigation 的事件机制。 目前还预留了名为 add 的中间悬浮按钮，但实际 tabConfig 中没有配置 add，所以这段逻辑目前不会触发。

4. API 请求封装

src/api/common/http.tsx 用一个 RequestHttp 类包装 Axios。 构造函数内创建 Axios 实例，并配置请求、响应拦截器。请求拦截器会从 MMKV 读取 token， 注入 Authorization: Bearer ...，同时注入设备 UUID 和平台信息。

响应拦截器假设后端返回结构为 { Status, Success, Message, Data }。 如果 Status 不是成功码，就调用全局 Toast 显示错误。

这里最需要修的是失败分支：当前写了 Promise.reject(data)，但没有 return，后续又返回了 data。调用方可能进入正常分支。 正确写法应是 return Promise.reject(data)。

5. 登录表单实现

src/components/login-form.tsx 使用 react-hook-form 和 zodResolver 做表单校验。两个字段是 account 和 password，校验规则只要求非空。

表单提交前先处理“记住密码”：勾选时把 account、password 和 remember 写入 MMKV；不勾选时删除这份缓存。然后调用页面传入的 onSubmit。登录页的 onSubmit 再调用 loginApi， 成功后写 token、写 userInfo，并 router.replace('/')。

实现上表单和登录请求分离得比较清楚，但明文保存密码是明显安全问题。另外登录按钮没有使用 loading 状态锁定重复提交，只靠全局 Toast 展示加载状态，快速点击可能发出多次请求。

6. 列表分页与维修工单页

src/app/(repair)/repair-order.tsx 是比较典型的业务页。它维护 list、hasMore、refreshing、pageRef 等状态，通过 queryByFilter('EM_REPAIR_ORDER_MNG') 拉取分页数据。

后端记录先经过 mapToWorkOrder 转成 UI 组件需要的 WorkOrder 结构。这个映射里做了很多兼容字段，例如 ID、Id、id、 RepairOrderId 都可作为主键来源。这说明后端字段可能不完全稳定，前端在页面层做了兜底。

列表组件 RefreshListView 基于 @shopify/flash-list 封装下拉刷新和上拉加载。 不过 handleEndReached 中 setIsLoadMore(true) 后马上 setIsLoadMore(false)，没有等待异步加载完成，因此防重复触发能力不可靠。 应让 onLoadMore 返回 Promise，或把加载状态交给父组件统一控制。

7. 新建维修工单实现

src/app/repair-order/add.tsx 使用大量本地 useState 管理表单字段，包括设备、故障类型、影响程度、优先级、描述、期望时间、维修人员、备注和是否停机。

页面加载时并行概念上加载 LOV、设备列表、维修人员列表，但代码实际是多个异步函数在 useEffect 中连续调用，没有统一 loading/error 状态。提交时通过 validateForm() 做手写校验，再用 buildSubmitData() 拼接后端需要的字段，最后 POST 到 /api/EmRepairOrder。

这个页面已经有较完整的业务流程，但表单复杂度开始超过纯 useState 的舒适范围。建议后续迁移到 react-hook-form，并把设备选择、维修人员选择、故障信息拆成子组件。

8. Toast 全局提示

src/components/ui/toast.tsx 实现了一个单例 ToastManager。 外部通过静态对象 Toast.success/error/info/loading/hide 调用， 根布局渲染 ToastContainer 后订阅 manager 的状态变化。

它的优点是没有引入额外库，调用简单。缺点是动画只用 opacity state 和 timeout 模拟， 没有真正的卸载动画；多个 Toast 只显示最新一个，之前的 Toast 仍在队列里直到各自定时器清理。 对当前项目够用，但复杂交互下需要更严格的队列策略。

9. 通用组件风格

Button 使用 tailwind-variants 定义 variant 和 size， 再通过 NativeWind 的 className 应用到 RN 组件。这个模式有利于统一 UI 样式，也方便测试时通过 testID 定位 label 和 loading indicator。

当前页面层仍存在大量手写 className 和颜色值，说明设计系统只覆盖了部分基础组件。 后续如果页面继续增加，建议把卡片、表单项、选择器、状态标签也沉淀为统一组件。
